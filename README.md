# 옥키 · 방 알림과 첫 1년

옥천 입사 예정·입사한 1인 청년의 방 찾기와 정착을 돕는 한국어 반응형 웹 시제품입니다. 방 알림 신청부터 상담, 공공주택 정보, 동네 Q&A와 입주 후 생활까지 이어지는 흐름을 제공합니다.

## 기존 시제품 화면

아래는 현재 제공되는 화면과 체험 기능입니다. 업무 데이터의 실제 저장·권한·알림 기능이 완성되었다는 뜻은 아닙니다.

| 기능 | 주요 내용 |
| --- | --- |
| 방 알림 | 입주 일정·예산·지역·생활 조건 등록, 조건 수정, 탐색 일시 중단·종료 |
| 공간 상담 | 안내받은 공간 확인, 신청 조건을 불러온 상담 요청, 진행 기록·취소 |
| 방 정보 제공 | 중개사 매물·퇴거 예정 정보 접수, 수정·철회, 운영 확인 체험 |
| 공공주택 | 주택·회차별 공고 탐색, 관심 주택 관리, 새 공고·모집 일정 알림 설정 |
| 동네 커뮤니티 | 일상·동네 정보, 질문·답변·답변 채택, 거주·방문 후기 |
| 정착·생활 | 첫 1년 할 일, 입주 상태, 저장한 정보, 생활권 도식과 최근 조회 장소 |
| 알림함 | 방 소식·질문 답변·할 일·공공주택 일정 알림 확인 |

양식의 임시 저장과 복원을 지원하며, 저장과 알림 구독은 별도로 관리합니다. 상담 요청은 방문·계약 완료와 구분합니다.

## 현재 구현 범위

기존 HTML·JavaScript·CSS 화면을 유지하고 Next.js 16.4.5 Route Handler로 Supabase Auth를 연결했습니다. 회원가입은 이메일·비밀번호·비밀번호 확인, 로그인은 이메일·비밀번호를 사용합니다. 가입 시 이메일 확인을 요구하지 않으며, 비밀번호 확인 입력은 화면의 일치 검사에만 사용하고 서버에 보내거나 저장하지 않습니다.

개발 프로젝트는 **Tech for impact - Develop** (ref: `osmxevxdsgvphqvdjnls`, 서울 `ap-northeast-2`)입니다. Auth는 Publishable key를 사용하고, 신규 신청 API는 서버 전용 SUPABASE_SECRET_KEY를 사용하도록 구현했습니다. 개발 DB에 접수 테이블·RPC·비공개 사진 버킷을 적용하고 실제 연동을 검증했습니다. 계정은 Supabase Auth에 저장되며, 세션은 HttpOnly·SameSite=Lax 쿠키로 관리합니다. HTTPS에서는 Secure도 적용합니다. 로그인 후 `#/account`에서 계정을 확인하고 로그아웃할 수 있습니다. Auth 응답은 UUID와 이메일만 반환하며, 이후 업무 API는 서버에서 검증한 UUID를 소유권 기준으로 사용해야 합니다.

**기존 체험 데이터는 localStorage에 남아 있으며 자동 이관하지 않습니다.** 네 신청 폼의 서버 저장·계정별 조회/수정/삭제·사진 업로드를 로컬 앱에서 실제 개발 Supabase와 연결해 검증했습니다. 커뮤니티 등 다른 기능은 기존 체험 데이터입니다. 다른 계정으로 로그인해도 같은 브라우저의 체험 기록은 공유됩니다. 운영자 화면도 체험용이며 실제 운영 권한을 부여하지 않습니다.

## 신청 저장 구현 상태 (2026-11-08)

- 로컬 구현: 네 폼 → 인증된 UUID → 서버 전용 RPC 저장, 계정 화면의 본인 목록/상세/수정/삭제, 별도 연락처·동의, Idempotency-Key·version, 비공개 사진 예약/재인코딩/업로드.
- 검증: check/test:ci 23개/build. PostgreSQL 엔진(PGlite)의 트랜잭션·제약·권한 테스트와 mock API/DOM 회귀이며 원격 실연동을 대신하지 않습니다.
- 개발 DB 적용 완료: 사용자 승인 후 application_intake와 intake_auth_boundary migration을 적용했습니다. 실제 Auth 쿠키 로그인 → 네 폼 저장/조회/수정/삭제, 멱등 요청·version 충돌, 타인 조회/수정/삭제 및 직접 Data API/RPC/사진 접근 거부를 확인했습니다. 사진은 실제 비공개 Storage 업로드·WebP 변환·서명 URL 열람을 검증했습니다.
- 실제 검증: scripts/verify-intake-live.mjs의 11개 점검 통과. 합성 계정 두 개와 해당 신청·사진을 삭제했고 잔여 신청/연락처/사진 0건을 조회로 확인했습니다. 재실행은 로컬 앱 서버와 INTAKE_LIVE_VERIFY=develop, VERIFY_APP_URL을 명시해야 합니다. 키·쿠키·번호·계정 식별자는 출력하지 않습니다.
- 보안 advisor: RLS 정책 없음 INFO 11건은 일반 사용자 직접 접근을 차단하는 의도된 구성입니다. 유출 비밀번호 보호 비활성 WARN 1건은 출시 전 확인 과제로 남았습니다. 개발 Preview 배포와 화면 검증은 아래 최신 기록을 참고합니다.
- 보관 정리: CRON_SECRET으로 보호한 POST /api/intake/maintenance를 추가했습니다. 만료 신청과 24시간 지난 미완료 사진을 정리합니다. 정기 호출 스케줄·실패 경보는 아직 연결하지 않았으며 실사용 전 필요합니다.
- 운영자 UI/권한·매칭 사진 조회·중개사 계정 발급은 후속입니다. 회원 탈퇴·백업 삭제와 외부 위탁/이전 조건의 출시 전 확인도 남아 있습니다.

## 앞으로 구현할 MVP

- [ ] **신청 저장:** 청년의 방 찾기 조건과 동의를 Supabase에 저장하고, 본인이 수정·종료할 수 있도록 합니다.
- [ ] **방 접수·검수:** 제공자의 방 정보를 저장하고 운영자가 공급 조건을 확인합니다.
- [ ] **운영자 관리:** 권한을 검증하고 신청자·방·상태와 이력을 관리합니다.
- [ ] **후보·안내:** 조건에 맞는 후보를 찾고 운영자가 승인한 방의 안내·문의·사양을 기록합니다.
- [ ] **최신성·지표:** 신청과 방의 확인일을 관리하고 운영 지표·CSV를 준비합니다.
- [ ] **보안·개인정보:** 계정별 접근 제어, 동의 이력, 로그인 방어, 삭제·백업과 출시 전 검증을 구현합니다.


## 보류 및 후속 단계

**당분간 사용하지 않음 — 사용자 결정:** 휴대폰 인증, SMS/LMS 및 문자 기반 재확인·무응답 만료. 네 신청 폼은 운영자의 직접 연락을 위한 신청자 전화번호를 인증 없이 입력받도록 변경했으며, 현재는 체험용으로 번호를 저장하거나 전송하지 않습니다. 따라서 문자 발송 outbox worker·웹훅·실제 발송도 활성화하지 않습니다. 원래 MVP의 문자 안내·전달 결과·48시간 차수 및 문자 재확인은 기능 재개와 D05·D07 등의 정책 확정 후 구현·검증합니다. 현재 개발 프로젝트는 이메일 확인 없이 가입하며, 이메일 소유를 검증된 것으로 간주하지 않습니다.

**MVP에 계획됐지만 일정에 따라 수동 대체 가능한 기능:** LH 공고 자동 수집·검수 후 안내, CSV 전용 UI, 목록 고도화, 재확인 자동화. LH 수집 범위와 자동 발송은 D08 확정이 필요하며 문자 보류 중에는 문자 발송하지 않습니다. 기존 정책 안내와 공공주택 시제품 화면은 유지합니다. (1·12~13·16·21장)

**후속 단계 검토:** 소셜 로그인·회원 프로필, 중개사 계정·대시보드, 자동 매칭 발송, 카카오 알림톡, 공공주택 신청 도움, 커뮤니티 채택·추천·보상 고도화, 자동 수요 보고서·실거래 API 분석. 이는 현재 구현 약속이나 확정 일정이 아닙니다. (1장)

**현재 MVP 제외:** 네이티브 앱, 지도 기능 개발, 결제, 채팅, 룸메이트 매칭, 공개 매물 목록. 기존 생활권 도식 등 시제품 화면의 존재와 실제 지도 서비스 개발은 구분합니다. (1장)

## 개인정보 초기 운영 기준

2026-11-08 설정한 [개인정보 방침 v1](docs/database-design.md#8a-초기-개인정보-운영-방침-v1--2026-11-08)을 구현 기준으로 사용합니다. 신청자 번호는 운영자 연락용, 집주인 번호·동호수·계약서·대화 원문은 미수집입니다. 신청은 최대 90일이며 목적 달성·종료·철회 시 먼저 파기하고 연장은 명시적으로 받습니다. 사진과 추가 조건은 선택 동의로 분리합니다. 실제 운영 주체·문의 창구·위탁/국외 이전·백업 및 보안 접속기록의 확인과 폼/API/삭제 기능 구현은 출시 전 필요합니다. 아직 실제 수집·보관·삭제 시스템에 적용한 것은 아닙니다.

## 미결정 사항과 구현 시점

상세 필드·권한·변경 이력은 [DB 상세설계](docs/database-design.md)를 기준으로 관리합니다. 아래 항목은 구현 시점을 구분한 목록이며, 실제 운영에 적용되었다는 뜻은 아닙니다.

### 실제 신청 접수 전에 필요한 작업

- [ ] **DB 저장과 접근 제어:** 로그인된 계정의 UUID를 서버에서 검증하고 신청·유형별 상세·동의·신청자 연락처를 단일 트랜잭션으로 저장합니다. 본인 소유권, 운영자 역할, 중복 제출과 동시 수정을 검증합니다. 기존 체험 데이터와 운영 데이터를 구분합니다.
- [ ] **운영자 권한과 연락처 조회:** 활성 운영자만 신청 내용과 인증되지 않은 신청자 번호를 볼 수 있도록 서버에서 매 요청마다 권한을 확인합니다. 번호는 운영자의 직접 연락에 사용하고, 일반 사용자·다른 신청자·분석 역할에는 공개하지 않습니다. 조회 이력, 로그에서 번호 제외, 삭제 절차를 마련합니다.
- [ ] **수집 범위·개인정보:** 신청자 전화번호는 운영자 연락용으로 수집하되, 상세 주소와 집주인 등 제3자 연락처는 필요한 항목·목적·접근자·제공 대상과 조건을 결정합니다. 현재 일부 체험 폼에 주소·집주인 연락처 입력란이 있으므로 실제 접수 전에 해당 입력과 보관 경로를 정책에 맞게 정리합니다. 제3자에게 신청자 번호를 제공하려면 별도의 구체적 동의가 필요합니다.
- [ ] **동의·보관·삭제:** 실제 수집 전에 개인정보 안내·동의 문구와 버전, 보관 기간, 철회·삭제 및 백업 복구 후 삭제 절차를 확정하고 구현합니다. 기간·동의 기본 문구는 DB 상세설계 8A에 정했으며 실제 기능 적용과 외부 조건 확인이 남아 있습니다.

### 해당 기능을 활성화하기 전에 필요한 작업

- [ ] **중개사 매물 등록 권한:** 중개사 등록을 실제로 받기 전에 자격 확인 담당자·근거, 계정별 권한 부여·정지·회수 절차를 정하고 서버에서 검증합니다. 현재는 매물 폼에서 중개사무소 정보를 받습니다. 옥키가 확인된 중개사 계정을 발급·운영하는 기능을 구현한 뒤 사무소 정보 입력란을 제거합니다. 일반 운영자 권한과 중개사 권한은 구분합니다.
- [ ] **사진 업로드·열람:** 실제 사진을 받기 전 파일 형식·크기·픽셀·개수 검사, 사진당 약 500KB~1MB 압축 목표와 방당 최대 5장 제한, 개인정보·위치정보 제거와 비공개 저장을 구현합니다. 매칭된 신청자가 해당 매물 확인 상세 페이지의 사진 영역에서 사진을 보도록 하고, 해당 안내에 접근할 권한을 검사합니다. 사진이 없거나 준비 중일 때의 화면도 처리합니다. 짧은 유효기간의 서명 URL과 서버 프록시 중 열람 방식을 결정합니다. 사진을 받거나 보여주지 않는 단계라면 해당 기능은 후속으로 둘 수 있습니다.
- [ ] **매칭·알림:** 실제 매칭과 웹 알림은 별도 구현합니다. 운영자의 직접 연락과 자동 문자 발송은 구분하며, OTP·SOLAPI는 재개 결정 전까지 사용하지 않습니다.

### 입주 후 거주 현황 확인 — 후속 기능

- 사용자 결정: 별도 선택 동의를 받는 후속 기능이며 **아직 구현하지 않습니다**. 방 안내·재신청과 참여 여부를 연계하지 않습니다.
- 입주 후 1·3·6개월에 본인이 거주 중/퇴거함/응답하지 않음을 답하는 방식을 제안합니다. 입주·퇴거 연월과 마지막 확인 시각만 최소 수집하고 퇴거 이유는 선택으로 둡니다. 계약과 실제 입주는 구분합니다.
- 미응답이나 계약기간 종료를 퇴거로 판단하지 않습니다. 응답자 기준 비율과 미응답 수를 구분하고 전체 입주자의 거주 유지율로 단정하지 않습니다.
- 기존 신청 보관기간을 일괄 연장하지 않습니다. 별도 동의한 참여자의 최소 조사 자료만 분리 보관하고 조사 종료·철회 시 개인 연결 자료를 삭제합니다. 도입 시 조사·보관 기간, 연락 방법과 철회 경로를 확정합니다.
- 계약서·주민등록 서류·GPS·집주인 확인을 강제하지 않습니다. 조사 원문은 본인/담당 운영자만 조회하며, 집계도 작은 집단의 재식별 위험을 검토합니다. 자세한 조건은 [DB 설계의 후속 기능 항목](docs/database-design.md)을 따릅니다.

### 옥천 공공임대 실제 공고 (2026-11-10)

`#/public`와 `#/public/list`는 DB에 저장된 실제 LH 공고만 표시합니다. 상세에서 유형·원문 상태·신청 전/신청 중/접수 마감·공고일·공고 마감일·옥천 공급 주소/주택형/면적/모집 수/가격 안내·원문 링크·안내사항·마지막 확인 시각을 확인합니다. 예시 공고를 실제 목록에 섞지 않습니다. 기존 체험용 관심/구독 데이터는 이관하지 않고 새 공공주택 알림도 제공하지 않습니다.

- 수집은 **수동 명령만** 제공합니다. 임대주택(06)과 주거복지(13) 전체 페이지를 조회하고 API가 적용한 검색 기간·중복·건수를 검증합니다. 기본 조회 범위는 현재 연도입니다.
- 충북/전국/지역 미상/옥천 후보의 공식 LH 상세 페이지에서 `충청북도 옥천군` 소재지를 확인하고 같은 단지의 공급행만 저장합니다. 제목만으로 판단하지 않습니다. 단지 없는 전세/매입임대 사업, 주소 미제공, 지원하지 않는 원문 형식은 미반영하며 운영자 검토는 후속입니다. 전체 옥천 공고를 빠짐없이 수집했다고 보장하지 않습니다.
- 공고·공급은 단일 RPC transaction으로 갱신합니다. 중복 방지, 변경 version 증가, 오래된 실행 차단. 조회에서 빠졌다는 이유로 삭제·취소하지 않습니다. 현재 데이터 보존이며 과거 전문 revision 보관은 후속입니다.
- `공고중`을 `신청 중`으로 추정하지 않습니다. 확인된 단지 일정/원문 접수 상태로 판정하고, 일정 불명·당일 접수시간 불명은 표시합니다. 접수마감은 계약·입주 종료가 아닙니다. 가격 `공고문 참조`/미확인은 0원이 아닙니다.

## GitHub Actions → Vercel 배포

저장소: [juno-gachon/Okki](https://github.com/juno-gachon/Okki)

PR에서는 CI 검사를 실행하고, 배포는 아래 브랜치의 push에서 실행하도록 구성되어 있습니다. 배포 workflow는 해당 커밋의 구문 검사·테스트를 통과한 뒤 Vercel CLI **65.11.0**으로 `pull` → `build` → `deploy --prebuilt`를 수행합니다.

| 브랜치 | GitHub Environment | Vercel 환경 |
| --- | --- | --- |
| `develop` | `preview` | Preview |
| `preview` | `preview` | Preview |
| `main` | `production` | Production |

개발은 `develop`에서 진행하고 `git push`로 Preview에 배포합니다. 검토가 끝나면 `develop` → `main` PR로 운영에 반영합니다. 기존 `preview` 브랜치 배포도 유지합니다.

`develop` 고정 주소: [개발 Preview](https://github-vercel-okki-develop-tech-for-impact.vercel.app). 배포 성공 후 별칭을 최신 배포에 연결하며, Preview 접근 보호 설정은 그대로 적용됩니다.

최초 설정:

1. Vercel 대상 프로젝트를 준비하고 Root Directory는 저장소 루트, Framework는 `Next.js`로 설정합니다. `vercel.json`은 `outputDirectory: ".next"`를 명시하여 이전 정적 사이트의 `src` 출력 설정을 덮어씁니다. 빌드 명령은 `npm run build`를 사용합니다.
2. GitHub Settings → Environments에 `preview`, `production`을 만들고, 각각 아래 값을 등록합니다. 환경별 프로젝트·비밀값을 구분합니다.
3. `preview` Environment의 배포 허용 브랜치에 `develop`과 `preview`를 지정하고, `production`은 `main`으로 제한합니다. `main`에는 CI 필수 검사와 브랜치 보호를 적용하고, `production`에는 배포 검토자를 설정합니다.
4. `develop` push 후 Actions 결과와 배포 페이지·스크립트·스타일 로딩을 확인하고, 검토한 변경을 `main`에 반영합니다.

| 등록 위치 | 이름 |
| --- | --- |
| Environment Secret | `VERCEL_TOKEN` |
| Environment Secret | `VERCEL_ORG_ID`, `VERCEL_PROJECT_ID` |

Vercel Git 자동 배포는 `vercel.json`에서 비활성화하여 Actions와의 중복 배포를 방지합니다. 실행 요약에는 커밋 SHA와 배포 URL이 기록됩니다. 실제 인증·DB·문자 연동은 별도로 구축·검증해야 합니다.

Auth를 Preview에서 사용하려면 Vercel의 **develop 브랜치 Preview 환경**에 위 네 변수를 설정해야 합니다. `APP_BASE_URL`은 develop 고정 Preview 주소를 사용합니다. 다른 임시 배포 URL에서 POST하면 Origin 검증으로 거부되므로 고정 주소로 접속합니다. `NEXT_NO_ROUTES_MANIFEST` 오류가 `src/routes-manifest.json`을 가리키면 이전 출력 설정이 적용된 것입니다. `outputDirectory: ".next"` 수정이 포함된 새 커밋으로 Actions를 실행해야 합니다. 대시보드의 Output Directory override도 해제하면 설정 혼동을 줄일 수 있습니다. production에 개발 DB 값을 복사하지 마세요. 코드도 `VERCEL_ENV=production`에서 위 개발 DB 연결을 차단합니다. 이번 작업에서는 Vercel 환경값·프로젝트 설정을 원격 변경하거나 배포하지 않았습니다.
